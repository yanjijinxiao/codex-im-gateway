# 流式排版、网页凭据与远程准入审批补修

基线 0b23629。用户的两张新截图分别指出：流式回复预览结构消失，以及账号页允许个人时 Invalid request token；随后指出待审批页不显示准入申请，远程无法访问本机管理地址。

## 1. 排版与摘要

此前 turn-progress-card 的 plainPreview 抹掉标题、加粗、列表和代码，随后 DingTalk 动态正文又做一次纯文本转换。answer() 还会把真实公开摘要改成通用“正在组织最终回复”。现有测试只保证流式控件安全，没有断言可读结构和摘要保留。

统一 markdownPreview 生成闭合的行内 Markdown：普通字号粗体标题、显式序号、缩进、行内代码、按列名呈现的表格行。代码预览最多 12 行，整体预算按 Unicode 字符计算；私有动作 JSON 隐藏。DingTalk 动态正文依旧是一个带 br 的原生段落，避免动态重写原生列表/表格/代码块控件时内容消失。静态 /stop 复制框及 IDE 页脚、原生圆环所属块和最终完整 Markdown 文档保持独立。真实公开摘要不再被通用占位句覆盖。

逐字符前缀、截断、HTML 注入、表格数据与代码、真实 REST/SDK 生命周期、等待/恢复/重启/最终结果均有回归。源码与 AST/传输检查不代表手机原生客户端已验收；未发送额外线上测试卡。

## 2. 网页跨重启的请求凭据

请求 token 每进程生成，长期打开的页面在部署后保留旧 token。旧页面第一次写入因此在 handler 前被拒绝。新增轻量只读 /api/request-context，保留 loopback、Host、Origin、CORS 和 no-store 限制。仅在 403 明确标记 request-token-invalid 且 not-submitted 时，网页合并重新握手并重试原点击一次；URL、JSON/FormData、来源 requestId 和审批对象不变。网络丢失、其他 403、500、已进入 handler 的失败均不自动重试。第二次 token 拒绝不循环。

旧版本已加载的 JavaScript 不可能自行获得补丁，部署后旧页面需刷新一次；新版页面以后可自动处理 token 轮换。没有延长 token、增设密码、重置 ACL 或公开管理端口。

同时补齐 IDE 管理 HTTP 的 v2 多目录 scope schema（此前只支持 64 位旧 scope）：授权与 prepare 两条入口均接受 v2，实际目录范围仍需精确匹配。真实 HTTP 测试拒绝缺失、错误、旧范围和畸形 scope，正确范围才发放授权/启动。

## 3. 准入审批与原生任务审批分工

待审批页原先仅投影 ChannelApprovalController 的活跃原生工具审批。它没有承载个人/群准入，所以不是账号页授权的另一个入口。

新增 AdmissionService，记录渠道已核验的个人来源、机器人 provider、来源聊天、不可复用申请 ID/版本、24 小时期限与处理边界。Web 与 IM 共用该申请及 AccountManager.allowSender 原有 ACL；IDE 仍从相同个人准入读取资格。消息、群成员/会话角色和 IDE 配对身份不自动获得准入审批管理权。

管理员只由本机受 mutation token 保护的管理页明确登记：本人先从机器人发送 /access identity，再在“待审批 → 远程准入管理员”选择已核验个人身份。之后从机器人私聊或群聊发送 /access，查看申请详情并选择个人、整个已核验群聊、拒绝。该入口在 session/普通 ACL 门禁前单独核验个人管理员资格，不依赖当前 session，不执行原申请消息。每个管理员仅能处理所属账号/provider 的请求；其他群成员即使复制整条命令也无权处理。

本机决策与远程决策使用不同显式方法，远程方法始终要求管理员；共同调用私有提交边界。写 ACL 前持久记录 applying；异常/崩溃后不自动重试。已确认 ACL 从 Web 与 IM 同步消失；拒绝、过期、版本不符、重复、管理员撤销、机器人变更均关闭旧操作。损坏记录不覆盖；账号删除清除其管理员，重新加入相同账号不复活旧管理权。记录限制全局 500、每人 8 个来源，重复消息不延长期限。管理员是独立资格，撤销普通准入不会隐式撤销管理员，网页明确说明单独撤销位置。

页面使用原生下拉框和提交按钮，无重复复制框、不默认选择范围；登记管理员独立确认。拒绝/准入均不重放用户旧任务。工具审批仍由原生控制器及原绑定聊天处理；没有把 /access 当作工具批准，也没有让所有已获准用户互相授权。

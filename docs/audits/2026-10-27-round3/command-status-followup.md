# 群命令与诊断延迟补修

用户截图指出两处此前审计没有覆盖的入口组合。基线为 9fdafbf。

1. 群消息 @ 后没有空格或换行，以及 /queue 紧接中文正文时，原适配器的 addressing 正则不能去掉前缀。消息以 @ 起头，因而被当成普通输入介入原轮次。共享 command-text 现在负责语法切分与群 addressing；queue/steer 的中文正文允许紧接命令，别名 iv 一致。普通段落、引用、代码、相似命令名、路径形式及参数中的 @ 不因此变成控制命令。
2. /status 原先顺序等待 Taskboard、config/read、完整 inspectThread（包括 Desktop owner 发现或全历史）。此外所有 slash 命令先等已安装 Skill 发现，部分渠道还先抓取引用正文。现在核心命令优先，扩展别名不能覆盖核心命令；诊断不解析引用附件。Taskboard、配置和元数据并行读取，回复预算为 1 秒，超时项明确未确认，不以缓存或默认值冒充当前事实。只读状态连接与执行/授权观察连接分离，独立的 3 秒 RPC 预算允许 SSH 冷连接完成初始化，后续查询仍重新读取。

/queue list 只核对本聊天，重复在途核对合并，结果超时则标明持久回执尚未确认。后台全账号核对保持独立；backend 更换不会复用旧 backend 的在途读取。实际入队仍使用既有原生接口、接收回执及来源核验；同时补齐准备期间 reset/rebind ABA 的队列核验。

验证：

- DingTalk text/richText 真实回调夹具覆盖紧邻 @、换行、NBSP、DWS mention、中文命令参数，以及普通文字/引用/代码不误路由。
- Bridge 到原生队列入口确认一次 add，不进入 run/steer，参数与 actor/conversation 保留。
- Skill 发现、引用抓取、Taskboard、runtime、状态同时不响应时，/status 在 1 秒预算后返回已知绑定及未确认状态；绑定重置时不展示迟到旧状态。
- 独立诊断读超时不关闭并行的授权/目录读连接；真实 JSONL 只允许 config/read 与已有只读方法，仍禁止写入和历史 hydration。
- 队列核对覆盖聊天范围、同 backend 并发合并、更换 backend、慢后端及时回执及准备阶段 ABA。
- 全量回归在补充最后一个队列列表用例前为 1681 项：1680 通过，1 项 Windows 专属跳过，0 失败；随后 9 个补修边界测试通过。最终发布制品门禁重新执行全部用例，并记录确切计数。
- 临时状态、假发送端与真实本机 Codex 只读诊断两次耗时 132ms/7ms；不包含 IM 网络投递时间，未发送测试卡，也未重放截图中的任务。

先前远程超时与本次命令误路由是不同缺陷；不能用上一轮传输修复替代本轮输入语法和诊断等待验证。

# 发布不能打断 Gateway 持有的原生任务

## 实际事件

Tokyo plan 的原生轮次 `01a182ef-97be-7371-961b-600ba737d177` 在北京时间 22:35:02 开始，23:04:28 收到原生 `turn_aborted`，原因为 `interrupted`。Gateway 在 23:04:27 开始停止，切换前仍有正常进展。这是发布关闭私有 app-server 所致的真实中断，不能用重置卡片状态、自动重发消息或伪造“已恢复”修复。

原生 rollout 与 `service.log` 的交叉记录确认了时间关系。该事件与 OpenClaw 的迟到队列回执卡不同；后者已按相同 message ID 原位关闭，并在钉钉客户端确认显示“状态已纠正”。

## 所有权与边界

- Gateway 的响应计数、Bridge 的消息准备/执行/队列派发、容量恢复、systemError 恢复和配置切换共同决定是否空闲。外部 Desktop 独立持有的任务无需随 Gateway 发布停止。
- 原进程在同一个同步执行段中检查空闲并关闭原生输入准入；IM、Web、原生队列及恢复流程复用现有可写检查。忙碌时返回 409，保留既有任务，不关闭 runner。
- 发布门禁需要本地管理端的 Origin 和请求凭据，绑定随机 release owner 与原进程 PID。另一个 owner 不能取消门禁。
- 本地发布把门禁写入独立的 release-admission.json；替换进程在暴露 HTTP 或初始化渠道前读取。渠道可连接并完成就绪检查，但新任务仍不能提交。验收成功、写入 verified 后再开放输入；开放后的错误不再自动停止新进程回滚。
- 验收前回滚需确认持久化门禁仍归本次发布所有，避免杀掉已经重新接收任务的替换进程。坏门禁文件、磁盘清理失败、HTTP 回执丢失均不能悄悄开放输入。进程/脚本崩溃不会按计时器自动解除门禁。
- 网页更新同样先检查空闲并持有内存准入门禁，安装失败或没有重启回调时释放。源码部署的网页入口仍不提供 npm 更新。

## 验证与边界

增加 test/release-admission.test.ts，覆盖忙碌任务、准备阶段、队列、两类恢复、配置、停止、错误 owner、鉴权、三个真实提交入口、带启用账号的替换进程启动、损坏/无法删除的门禁文件、回滚保护、旧版不支持、PID 改变、丢失回执、更新失败。测试只使用隔离目录、临时 HTTP 服务和合成 runner。

修改前先运行首批 9 项回归，9 项失败（缺少 prepareRelease/cancelRelease API，HTTP 404），记录在 /private/tmp/gateway-release-admission-baseline.log。实际旧版不能证明安全时，正常 release-local switch 必须在停止服务前失败，不能静默降级为仅查询空闲状态。

全量测试、类型检查、隔离构建、制品哈希和具体部署验收以对应 release manifest/log 为准。定向用例通过不等于覆盖所有执行时序。

## 第一次启用的迁移限制

线上 f179e9f 不理解新门禁协议，不能直接用新 switch 强行停止。首次升级只能在独立维护阶段先暂停所有渠道接收，确认既有 Gateway 任务已排空、没有启动中/结果不明的原生提交、恢复任务已停止准入，保留排队回执和输入。恢复账号原有 enabled 配置不能重启旧渠道接收；先创建新进程能够识别的持久化门禁，再用已有制品校验及切换流程安装。新进程完成验收后，通过原 owner 解除门禁。后续发布统一走正常原子门禁，不保留强制绕过开关。

不能因新功能写完就声称旧的 Tokyo 执行已经继续；继续原对话需要人的明确指令，且不能自动重发执行结果不明的输入。

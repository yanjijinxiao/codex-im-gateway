# Gateway 第二轮自检（2026-10-27）

本轮修复状态：第 1、7 项已按统一生命周期观察端口与普通消息透明转发边界修复；第 2 项已补普通 IM 准备后的绑定/权限核验，第 5 项已统一 Desktop 原生队列策略和菜单。第 3、4、6 项仍是独立待处理项，本次不宣称全部架构问题已解决。下文保留发现时的证据及代码位置，当前实现与验证契约见 im-channel-architecture.md。


检查基线：269b403。范围仅 Gateway，包括其与原生 Codex、渠道及内嵌 Taskboard 的接口；不检查 Farming，不把 Taskboard 独立子工程的测试基线算入 Gateway 验收。本轮是自检与缺陷复现，没有修改运行代码、提交、push 或切换线上版本。

## 一、整体架构

本轮确认了三处需要统一的架构边界，而不仅是某个函数少判断一次。

1. **身份查询、持久化历史和执行终态的权威没有分清。** 历史接口能找到 clientUserMessageId/turnId，并不表示它知道另一个进程中的执行状态。队列恢复把旁路历史当成终态，随后展示层冻结，实际 owner 的活跃状态无法纠正这次错误收尾。
2. **提交与生命周期保护没有覆盖所有执行入口。** 排队、普通 IM、Web 和容量恢复各自核验不同条件；普通 IM 漏掉准备后的权限与完整绑定，配置屏障漏掉容量恢复，统一停止漏掉 starting 账号。需要统一的执行登记与提交核验边界，涵盖准备、发送、接收与观察阶段。
3. **能力与重配置策略仍散落在入口。** /queue、/policy queue、ask 菜单各自判断 Desktop 能力；配置切换的准备、提交、启动和失败恢复也未形成一个完整事务。

以下列出的是已由代码、隔离诊断或线上只读对照确认的问题，不把文件长度或圈复杂度本身列为缺陷。

## 二、模块实现与遗漏场景

### 1. P1：原生排队被错误判为中断，进度提前关闭

**现象与证据：** 用户截图中的“已中断”卡对应同一原生轮次。只读核验时，Codex App 返回该轮次 inProgress，原生日志仅有 task_started；独立 App Server 的 thread/turns/list 却返回 interrupted。Gateway 的原生队列回执已记为 completed / delivered，卡片检查点也已 finished / interrupted。这是状态来源冲突，不是用户真的停止了任务。

**代码位置：** src/bridge/native-queue.ts:123–127 直接把历史中非 inProgress 状态转换为 completed；同文件:164–165 对 terminalObservation 跳过 Desktop / active 检查。src/codex/runner.ts:241 的 observeOnly 又允许从旁路后端取终态。src/codex/app-server-runner.ts:999 起用旁路历史观察该轮次，interrupted 随后被解释为执行错误。

**持续影响：** src/channels/progress.ts:268 的 finished 提前返回，以及 src/server/thread-event-hub.ts:312 起对已 finished 检查点的恢复限制，使后续真实进度无法继续写入这张卡。错误终态还触发了参与者 @ 提醒。

**后续追问投递核验：** 原会话记录确认收到了用户的“这是啥”和“排队以后，为什么只有中断？没有进度？”两条后续消息，并产生了对应 commentary 回答。钉钉截图却只有相同 turn 的接收回执，说明消息接收和回答送达脱节。原生接收成功不能替代回答的渠道投递确认；已错误结束的卡片会同时挡住后续进度与追问回答。

**隔离复现：** 提供“旁路历史 interrupted、Desktop owner active 且 activeTurnId 相同”的组合，现有恢复器仍把回执转成 completed 并进入结果投递。线上只读对照独立确认了同类状态组合。

**修复方向：** 历史只定位身份；执行终态必须带实际 owner 或明确原生生命周期结束证据。状态冲突时保留观察状态，不发停止卡、不宣布投递完成。对已确认的错误终态，应按精确 host/thread/turn 修复展示，保留旧卡记录及投递去重证据，不重放输入。回归需覆盖 live owner 与旁路历史冲突、owner 不可用、真实中断、真实完成、重启及终态纠正。

### 2. P1：普通 IM 在准备期间变更绑定或权限，仍可提交

**代码位置：** src/bridge/service.ts:2349 的 stillBound 只检查渠道未停止和 managed session ID；:2446、:2459 的最终提交检查复用它。它没有像 queue 路径那样核验原生 thread、host、来源 actor 准入和角色。

**隔离复现：** 用屏障暂停远程附件准备，分别执行：同一个 managed session 改为另一个 thread、将 actor 改为 viewer、撤销 actor 准入。三种情况均仍调用 runner.run，目标仍是准备前的 thread。第一种还会被 :2462 的结果写回恢复为旧 thread。

**影响：** 撤销权限后仍可能产生新执行；同一记录重置/改绑期间可能向旧线程发送并覆盖新绑定。

**修复方向：** 普通 IM、显式 queue、steer、Web 和工作流共用同一提交前核验契约。冻结来源与预期绑定，在最后一次外部写入前重查完整身份、权限和生命周期；接收后回调写入使用条件更新，不能覆盖新的绑定代次。新增远程转存屏障、改绑、换 host、撤权和改角色用例。

### 3. P1：配置切换没有登记容量自动恢复中的工作

**代码位置：** src/server/account-manager.ts:489 检查 respondingSessions 与 BridgeService.hasInFlightWork；容量恢复由独立的 CapacityRecoveryCoordinator 驱动，没有登记到这两个集合。:509 仍会关闭共享 runner。

**隔离复现：** 保持一个已获接收的容量恢复轮次不结束，再调用 reconfigureRuntime。配置回调仍执行，runner.close 被调用一次。

**影响：** 上一轮新增的配置屏障能保护普通 Web/IM，却仍可能打断自动恢复任务。

**修复方向：** 引入统一的运行工作登记/生命周期租约，覆盖直接提交、队列消费、容量恢复、准备与未确认接收；所有执行来源参与同一配置切换核验。测试应包含恢复尚未接收、已接收、等待交互、终态未投递与并发配置操作。

### 4. P2：统一停止跳过尚在连接中的账号

**代码位置：** src/server/account-manager.ts:479 的 stopAll 只选择 status === running 的账号；:501 的重配置选择同样只覆盖 running。

**隔离复现：** 账号 monitor 保持 connecting，startAccount 返回后调用 stopAll；其 AbortSignal 仍未 abort，entry 仍为 starting。

**影响：** 启动失败清理或配置切换时可能保留旧连接与旧服务对象。停止后继续到达的事件和旧配置回调也未获得完整生命周期隔离。

**修复方向：** 按资源是否存在而非 UI 状态枚举停止账号；每账号串行化 start/stop/refresh/remove，并为旧 monitor 回调加代次校验。覆盖 connecting、error、重连与并发开始/停止。

### 5. P2：排队能力在命令、策略和菜单中不一致

**代码位置：** src/bridge/service.ts:1662 仍因 desktopOwned 拒绝 /policy queue；:1699 的 canQueue 仍排除 Desktop。

**隔离复现：** 后端明确声明 nativeQueue 可用且 owner 为 Desktop，/policy queue 仍返回“不支持可靠的原生队列”；ask 策略也没有提供排队选项。

**影响：** 显式 /queue 与策略/交互菜单给出互相矛盾的能力说明。

**修复方向：** 用后端返回的、针对当前 owner 的操作能力作为唯一入口，统一命令、策略校验及菜单选项。覆盖 Desktop、Gateway 私有执行进程、共享 daemon、远端和纯 exec；纯 exec 缺少原生协议时仍应明确拒绝。

### 6. P2：Taskboard 替换配置先停服务，后验证新配置

**代码位置：** src/taskboard/lifecycle.ts:15 关闭并清除原服务，:19 才验证新 URL。src/server/http-server.ts:802 在应用服务配置后才持久化 Gateway 配置，也没有失败恢复旧运行态的事务边界。

**隔离复现：** 注入一个可正常关闭的旧服务，提供非 loopback 的替换 URL；apply 抛错时旧服务已经关闭，当前 service 为 undefined。

**影响：** 一次失败的配置操作即可造成服务下线，而持久配置仍可能保留旧值。

**修复方向：** 先完整验证和准备替换资源，再提交并切换；失败时明确恢复旧运行态或报告降级状态。测试应注入 URL 不合法、端口占用、启动失败、保存失败与旧服务停止失败。本项仅涉及 Gateway 拥有的集成生命周期。

### 7. P1：切项目与具体工作混合的自然语言请求被截断

**用户现象：** 请求在指定项目创建 session、review patch 并为该 session 建群，Gateway 只切换项目，返回模式选择菜单，后续工作没有进入执行。

**代码位置：** src/bridge/ai-channel-intent-decision.ts 的 action 模型没有用于保留剩余普通任务正文的字段；src/bridge/channel-command-policy.ts:66 仅在 plan on 或 goal set 时允许命令后继续对话；src/bridge/service.ts:441 执行友好命令后直接返回。项目选择展示菜单发生在同文件:945 起。

**隔离复现：** 分类结果仅识别 project switch，或同时识别 project switch 与 mode session，给出包含 review 和建群要求的完整原消息；两种情况下项目均切换，但 runner.run 调用为 0。诊断注入合法分类结果以验证分发边界，没有再次执行用户截图里的工作，也不把模型对历史消息的实际分类输出当成已取得的日志。

**用户明确的职责边界：** 没有 / 控制命令前缀的普通自然语言，应完整交给当前 Codex 会话。Gateway 不应利用意图分类将它截获并改成项目或模式操作。

**修复方向：** Gateway 控制分发只处理显式 / 控制命令和可信原生交互；退出普通自然语言的控制意图分类路径，保留文本、附件和引用的完整上下文。执行中的普通消息按原生 steer 契约提交，无绑定时明确提示。自然语言中要求创建 session、review、使用 skill 或建群，由 Codex 自身处理。补纯自然语言、包含命令名称但不以 / 起头、混合任务、未知 / 文本、可信卡片回调及跨主机转发的用例。

## 验证结果与修复顺序

当前版本全量根测试重跑：1601 项，1600 通过、1 项 Windows 平台专属跳过、0 失败，包含隔离真实 Codex 的原生队列测试。

本轮原有 9 个临时诊断用例，以及截图追查新增的 2 个混合意图用例，共 11 个，分别确认上述缺陷仍存在。它们断言的是问题行为，不能作为“修复后通过”的回归计数，也不能加入正常发布门禁后继续把问题行为视为正确。

诊断材料位于本机 /private/tmp/gateway-second-audit.le2soJ，包含边界、生命周期、队列与配置三个诊断文件及输出日志；使用临时账号、假后端和屏障，不提交真实用户任务。线上只读对照仅用于确认当前截图轮次的状态冲突。

修复顺序：先处理队列终态权威和错误卡恢复、普通提交的权限/绑定核验，再统一执行生命周期与账号停止；随后统一排队能力及配置切换事务。每项先把诊断改成正确行为的回归断言，再进行组合回归和发布前验证。本轮结论是仍有这些明确问题，不是所有模块已经无缺陷。

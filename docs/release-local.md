# macOS 本机服务的隔离发布

`scripts/release-local.mjs` 管理已有 launchd 服务的 prepare → seal → switch → verify。它不是跨平台安装器；首次安装及手动前台运行见 local-run.md。

每一步显式传入同一组 `--dir`（新的独立发布目录）、`--state`（实际状态根）、`--origin`（回环管理入口）、`--service`（launchd domain/label）与 `--plist`（现有 plist 绝对路径）。发布目录不可与源码或状态目录互相包含。服务端口、状态目录和 label 不从别的安装猜测；不要把示例默认端口当作现网配置。

1. 完成修复、复现与回归，提交最终源码。工作树不得有影响构建的未提交输入。
2. prepare 在独立目录运行类型检查、全套 Gateway 测试和构建，记录提交及制品散列，不覆盖运行中的 dist。需要原生 queue 集成时，显式设置 `CODEX_NATIVE_QUEUE_TEST_BIN`，测试仍只用隔离 Home 和本机假模型。
3. prepare 成功后 push 最终提交；seal 核对 origin/main 与制品提交一致。准备后源码再变更就重新准备，不能手改 manifest 冒充新制品。
4. switch 等旧服务退出后才替换制品并启动同一服务。保留旧代码；不恢复旧状态文件、不重放任务。关闭私有执行客户端仍可能中断其正在持有的任务，不能承诺所有原生执行跨进程继续。
5. verify 核对新 PID、`/api/build`、制品身份、账号、精确绑定、浏览器授权指纹/期限及 IDE 端点。只有验证成功才报告上线；失败按脚本回滚代码，保留当前状态。手机端网络与渲染需单独验收。

同一状态目录的 release.lock 排他覆盖每次命令及其异步工作。正常退出释放；崩溃遗留时会拒绝后续发布。先核实锁中 PID 的进程与发布操作已退出，再由运维清理；不自动抢占锁，也不能因为等待较久就删除。

普通 `build:bridge` 在编译前清理旧输出和封存身份。编译失败后不能继续用残留目录启动服务；重新成功构建或使用保留的已验证制品。普通构建没有封存 release 身份，仅隔离发布准备产生新 manifest。回滚代码也不等于回滚浏览器授权格式，旧版不支持新格式时应明确拒绝访问而保留文件。
